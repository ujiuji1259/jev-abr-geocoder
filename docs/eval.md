# 評価セットと指標

`config.py` の閾値を勘で決めないため、そして **trie + Jev という方式が本当に効いているのかを測る**ための仕組み。

実装と並行して用意する。評価セットが無い状態で閾値を触ると、必ず手元の数件に過適合する。

---

## 1. 用途の違うものを混ぜない

評価セットを4種類に分ける。**混ぜると、どれも信用できなくなる。**

| Tier | 入力 | ラベルの出所 | 件数 | 用途 | CI |
|---|---|---|---:|---|---|
| 0 | 合成（ABR から逆生成） | 自明（金） | 任意 | 回帰検出 | ○ |
| 1 | geolonia `list.txt` | 3者多数決（銀） | 7,191 | 難例の再現率 | ○ |
| 1' | 法人番号公表データ | `cityCode`（金）/ `postCode`（弱） | 任意 | 市区町村の正解率・大量評価 | × |
| 2 | Tier 1/1' の**不一致集合** | 人手（金） | 200〜500 | **閾値決定** | ○ |

---

## 2. 絶対に守る2つのルール

### ルール1: Jev で正解ラベルを作らない

Jev を評価するために Jev を使うのは循環論法。銀ラベルの生成に使ってよいのは、**Jev を使っていない別実装**（公式 abr-geocoder、geolonia）だけ。

### ルール2: Tier 0 で閾値を決めない

合成データには**自分が想定した表記ゆれしか現れない**。「面かげ」「七番丁の誤字」のような本物のミスは出てこない。

Tier 0 で閾値を決めると、数字は良く見えるのに本番でズレる。**Tier 0 は「実装が壊れていないこと」の確認だけに使う。** 閾値は Tier 1/1'/2 でのみ決める。

---

## 3. Tier 0 — 合成データ（CI回帰）

ABR の正規表記から出発し、既知の表記ゆれを**逆適用**して入力を作る。正解は自明。

```
「鳥取県鳥取市面影一丁目1番2号」
  → 「鳥取市面影1丁目1-2」        都道府県省略・算用数字・ハイフン
  → 「鳥取県鳥取市面影１丁目１－２」 全角
  → 「鳥取県鳥取市面影一丁目1-2 〇〇ハイツ301」 建物名付加
```

**索引側のエイリアス生成規則（`index/keys.py`）と対になる。** エイリアスを増やしたら、対応する合成パターンも増やす。

用途は「昨日通っていたものが今日も通るか」だけ。**精度の数字として報告しない。**

## 4. Tier 1 — geolonia `list.txt`（難例カタログ）

[geolonia/normalize-japanese-addresses](https://github.com/geolonia/normalize-japanese-addresses) の `test/addresses/list.txt`。**7,191件の入力**で、人間がキュレートした難例が含まれる。

```
和歌山県和歌山市7番町19                「七番丁」の誤字
京都府宇治市莵道森本8−10              莵と菟のゆらぎ
串本町串本千二百三十四                  都道府県無し&郡無し
岩手花巻市１２丁目７０４                「県」を省略
千葉県巿川巿巿川1丁目                  市(し)と巿(ふつ)のゆらぎ
東京都千代田区神田美土代町９番地７千代田２１ビル７階   「7千代田」が「7000代田」にならないこと
```

うち **49件には「何を試しているか」の備考が付いている**。カテゴリ別に精度を出せるので、Jev が効くと期待した箇所で実際に効いているかを診断できる。

| 件数 | カテゴリ |
|---:|---|
| 11 | 京都の「一号」が「一番町」に正規化されてはいけない |
| 6 | 町丁目内の「町」の省略 |
| 4 | 大字◯◯と◯◯町が共存 |
| 3 | サフィックスなし丁目とプレフィックス一致町の衝突 |
| 2 | 都道府県無し&郡無し / 莵と菟のゆらぎ / 途中にスペース |

### `addresses.csv` は正解データではない（重要）

同ディレクトリの `addresses.csv`（7,190件の期待値つき）は**使わない**。`build-test-data.ts` を読むと分かるとおり、

```ts
const result = await normalize(address)                        // geolonia 自身の実装を走らせて
output.push([address, result.pref, result.city, result.town])  // その出力を期待値にしている
```

**自己出力のスナップショット回帰テスト**であり、独立に検証された正解ではない。これを正解として採用すると、測れるのは「geolonia との一致率」であって正しさではなくなる。

ただし**第三の意見としては有用**なので、§6 の多数決に投入する。

## 5. Tier 1' — 法人番号公表データ（大量・半自動ラベル）

[国税庁 法人番号公表サイト 全件データ](https://www.houjin-bangou.nta.go.jp/download/zenken/index.html)。約490万件。リソース定義書 (`k-resource-dl.pdf`) で確認した列：

| 列 | 項目 | 評価での役割 |
|---|---|---|
| 18 | `streetNumber` 国内所在地（丁目番地等） | **入力**。人間が入力した生の住所（最大300字、建物名込み） |
| 16/17 | `prefectureName` / `cityName` | 入力の組み立て |
| 21 | `cityCode` 市区町村コード (JIS X 0402) | **市区町村の金ラベル** |
| 22 | `postCode` 郵便番号 | 町字の**弱いラベル** |

`cityCode` は JIS 5桁。ABR の `lg_code`（全国地方公共団体コード 6桁）へはチェックディジット計算で決定的に変換できるため、**市区町村レベルの金ラベルがラベル付けコスト0で約490万件手に入る**。

`postCode` は仕様書に「国内所在地の文字情報を基に設定」とあり、**国税庁側が住所文字列から導出した結果**。金ラベルではない。町字候補を絞る制約としてのみ使う。

これで答えられる一番大事な問い: **trie の再現率は足りているか**（正解の町字が候補集合に入っているか）。これは Jev の性能とは独立に測れる。

## 6. Tier 2 — 不一致集合（閾値決定の本体）

同じ入力を3者に流し、**割れたものだけを人手で見る**。

```
入力: list.txt + 法人番号データ

  ① 本実装（trie + Jev）
  ② デジタル庁公式 abr-geocoder (Go)      … Jev を使わない独立実装
  ③ geolonia addresses.csv                … 該当する入力について

全員一致 → 銀ラベルとして自動採用（= Jev を呼ぶまでもない簡単な例）
割れた   → ★ここが評価セットの本体
```

**Jev 方式が勝つか負けるかの境目は、すべて不一致集合にある。** 一致した大量のケースは簡単な例なので、人手を投入する価値は無い。200〜500件なら現実的な工数で、しかも**難例だけを自動で抽出できている**。

2者より3者のほうが不一致集合が鋭くなるので、`addresses.csv` はここで使う。

## 7. 指標

### 正解率（粒度別）

| 指標 | 一致条件 |
|---|---|
| 市区町村正解率 | `lg_code` |
| 町字正解率 | `lg_code` + `machiaza_id` |
| 番号正解率 | 上記 + `blk_id`/`rsdt_id` または `prc_id` |

### 再現率と精度を分けて見る

- **候補再現率** — 正解が候補集合（Jev に渡す前）に入っていた割合。**trie の責任範囲**
- **選択精度** — 候補再現率が満たされた中で、Jev が正解を選べた割合。**Jev の責任範囲**

この2つを分けないと、精度が出ないときに trie を直すのか質問文を直すのか判断できない。原則「trie は再現率だけを担保する」を数字で追跡する装置でもある。

### カバレッジと運用指標

- **カバレッジ** — `resolved=True` の割合
- **選択的精度** — `resolved=True` のうちの正解率
- **ファストパス率** — Jev を呼ばずに済んだ割合
- **Jev 往復数 / バッチ** — 設計上は高々2。退行したら落ちるようテストで守る
- **1件あたりコスト**、**p50 / p95 レイテンシ**

---

## 8. 閾値の決め方

`config.py` の `town_confidence` / `number_confidence` / `contains_answer` は、**精度-カバレッジ曲線から選ぶ**。

```
閾値を 0.0 → 1.0 でスイープし、各点で
    x軸: カバレッジ      resolved=True の割合
    y軸: 選択的精度      resolved=True のうち正解の割合
をプロットする。

用途に応じた動作点を曲線上から選ぶ:
  - 自動処理に流す      → 精度を優先し、落ちたぶんは人手に回す
  - 地図に置くだけ      → カバレッジを優先し、粒度を1段上げて返す
```

閾値は**単一の正解値ではなく、選んだ動作点**である。`config.py` のコメントに、どの曲線のどこを選んだかを記録する。

## 9. 置き場とライセンス

```
tests/data/
├── synthetic/          Tier 0。生成スクリプトのみ置き、成果物はコミットしない
├── geolonia/
│   ├── list.txt        Tier 1 入力（MIT, Copyright 2020 Geolonia Inc.）
│   ├── addresses.csv   §6 の第三の意見としてのみ使う
│   └── LICENSE.txt     原ライセンスの写し
├── hard/               Tier 2。人手確認した金ラベル
└── abr/                鳥取県 pref31 と佐々町 city423912 の実ファイル（単体テスト用、約2MB）
```

- **geolonia** — MIT。著作権表示とライセンス全文を同梱すれば再配布可
- **法人番号公表データ** — 国税庁。**利用規約の確認が必要**。確認するまでリポジトリにコミットしない（`.gitignore` で除外し、取得スクリプトのみ置く）
- **ABR** — [利用規約](https://www.digital.go.jp/policies/base_registry_address_tos)

CI で回すのは Tier 0 / 1 / 2 のみ。Tier 1' は大きいので手元とバッチ評価でのみ回す。

## 10. 着手順

**Tier 1 → Tier 0 → Tier 2 → Tier 1'。**

`list.txt` の 7,191件は取得済みで**今すぐ回せる**。法人番号データのダウンロードと利用規約確認より先に着手できるので、これを最初の的にする。

Tier 1' は「大量に回して統計を取る」段階になってから。
