# jev-abr-geocoder アーキテクチャ

日本の住所文字列を [アドレス・ベース・レジストリ (ABR)](https://www.digital.go.jp/policies/base_registry_address) に基づいて正規化し、緯度経度を返す。地番まで解決する。

本書に載せた数値はすべて実データでの実測値であり、根拠となる測定条件を併記する。

---

## 1. 基本方針

**ABR をトライ木として持って前方一致で候補を絞り、候補を [Jev](https://typesafe.ai/blog/introducing-system-one-models-and-jev) の Choice に渡して最も近い住所を選ばせる。**

この方針から2つの設計原則が導かれる。

### 原則1: トライは再現率だけを担保する

トライは「正解を候補集合に含める」ことだけに責任を持ち、**どれが正解かの判断はしない**。判断は Jev に一任する。

トライ側で精度を上げようとすると、閾値やスコアリングの調整が必要になり、その調整は住所表記のロングテールを永久に追いかけることになる。候補を広めに出して Jev に選ばせるほうが、コードが単純なまま精度が上がる。

### 原則2: 手書きの正規化ルールを置かない

住所の表記ゆれ（異体字・漢数字・ヶ/ケ・大字の有無）を吸収するための変換テーブルをコードに持たない。代わりに、

- **索引側のエイリアス展開** — ABR 自身が持つ列（`chome_number`, `county`, `*_kana`）から機械的に鍵を増やす。ロジックではなくデータなので壊れない
- **Jev の判断** — 残りの揺れは候補を見せて選ばせる

手書きの変換テーブルは永久にメンテナンスが必要で、漏れたときに黙って失敗する。これは TypeSafe のドキュメントが「fragile なパースコードをモデル判断に置き換えろ」と述べている対象そのものである。

入力側に残す正規化は **NFKC 正規化と空白の除去だけ**。判断を含まない機械的変換に限る。

## 2. 全体パイプライン

```
入力: "鳥取市面かげ1-2-3 〇〇マンション301"
  │
  ├─ ① 正規化          NFKC + 空白除去のみ
  │
  ├─ ② 住所トライ      完全一致 2 方向で町字候補を取得    層1 (town.marisa 24MB, mmap)
  │      索引鍵が入力の先頭 / 入力が索引鍵の先頭
  │
  ├─ ③ Jev Choice      町字を確定 (候補 ≤ 255)           確信度つき
  │      「該当なし」は予約オプションとして同じ分布に載せる
  │
  ├─ ④ 番号ストア      (lg_code, machiaza_id) で街区/住居番号/地番を取得   層2 (abr.db, 1-2GB)
  │
  ├─ ⑤ Jev Choice      数値テールを実在レコードに割り当て
  │
  └─ 出力: 正規化住所 + ABR 識別子 + 緯度経度 + 粒度 + confidence
```

②③ と ④⑤ の間には依存関係があるため、Jev の往復は最大2回。ファストパス（後述）が効いた場合は0回。

## 3. データ層

データ取得元は DCAT フィード `https://dataset.address-br.digital.go.jp/api/feed/dcat-us/1.1.json`（9,345 データセット）。実体は `https://data.address-br.digital.go.jp/` 配下の zip 圧縮 CSV。

| ABR ファイル | 内容 | 配布単位 |
|---|---|---|
| `mt_pref` / `mt_pref_pos` | 都道府県 (47) | 全国一括 |
| `mt_city` / `mt_city_pos` | 市区町村 (1,918) | 全国一括 |
| `mt_town` / `mt_town_pos` | 町字 (727,429) | 全国一括 / 都道府県別 |
| `mt_rsdtdsp_blk` (+`_pos`) | 街区符号 | 都道府県別 47 |
| `mt_rsdtdsp_rsdt` (+`_pos`) | 住居番号 | 都道府県別 47 |
| `mt_parcel` (+`_pos`) | 地番 | 市区町村別 1,887 |

座標はすべて `EPSG:6668` (JGD2011) の代表点。地番の座標も取り込む。

### 3.1 層1: 住所トライ `town.marisa`

対象は `mt_pref` / `mt_city` / `mt_town`。実装は [marisa-trie](https://github.com/pytries/marisa-trie)（LOUDS 簡潔トライ）の `RecordTrie`。

**実測**（全国 `mt_town_all.csv`、727,358 町字、エイリアス込み 2,268,688 鍵）:

| 実装 | 常駐メモリ | ディスク | 構築 | 前方一致1回 |
|---|---:|---:|---:|---:|
| 素の dict トライ | 1,322 MB | — | 80 s | — |
| ソート済み配列 + bisect | 約 165 MB | — | 即時 | 8.2 µs |
| **marisa-trie** | **1 MB** (mmap) | **12.9 MB** | 4.0 s | **5.3 µs** |

marisa-trie を採る。**全国の都道府県 → 市区町村 → 町字が 1 つのファイルに収まり、mmap ロードが 0.2 ms、常駐 RSS が 1 MB**。

> 実装後の実測: エイリアス規則を確定させた結果、鍵は 4,817,051 本、
> ``town.marisa`` は **24.3 MB**、構築は全国で 76 秒（ダウンロード済みから）。
> 上表は規則確定前の 2,268,688 鍵での測定値。

API サーバではこれが決定的に効く。mmap されたファイルは**ページキャッシュ経由で全ワーカーが同一の物理メモリを共有する**ため、ワーカーを何本立てても層1のコストは 13 MB のまま変わらない。起動が 0.2 ms なのでスケールアウトとローリング再起動も軽い。

#### エイリアス生成規則

1町字あたり平均 6.6 本の鍵を張る（全国 730,807 町字 → 4,817,051 鍵）。掛け合わせは以下の直積。

| 軸 | 変種 |
|---|---|
| 都道府県 | なし / `岩手県` / `岩手`（接尾辞を落とした形） |
| 郡 | あり / なし（郡がある市区町村のみ） |
| 丁目 | 原文 / `1丁目` / `一丁目` / `1`（`chome_number` 列から生成） |

**大字・字の接頭辞は直積の軸にしない。** この直積を、接頭辞の付け方 2 通り（**原文そのまま** / **両方落とす**）それぞれについて作る。

軸にすると「大字は原文どおり書くが字は省く」という混ぜた形まで張ることになるが、そんな書き方は実在しない。大字・字の両方に接頭辞がある町字は全国 57,033 件（7.7%）あり、そこが 4 通りに膨らんでいた。

| | 索引鍵 | `town.marisa` |
|---|---:|---:|
| 接頭辞を軸にする | 5,228,310 | 26.3 MB |
| **付け方 2 通りで張る** | **4,817,051** (−7.9%) | **24.6 MB** |

評価セット 2 つで**候補集合は 1 件も変わらなかった**（Jev への入力トークンが 191,953 / 1,108,729 と両者で完全に一致。プロンプトが変わっていない＝候補が変わっていない）。

なお ABR は**大字の列にも「字」を入れてくる**（全国 21,315 件。`真狩村字光`）。落とす対象は大字側も `大字` と `字` の両方。

**丁目は漢数字と算用数字の両方を必ず張る。** ABR の `chome` 列は表記が揺れており、「一丁目」のこともあれば「１丁目」のこともある。どちらで収録されていても両方で引けるよう、`chome_number` 列から生成する。これを入れる前は「東京都目黒区自由が丘二丁目」が引けなかった（ABR 側が `２丁目`）。

**市区町村の省略は索引しない。** 曖昧さが大きすぎて候補を絞れなくなるため。

ペイロードは町字レコードへのインデックス (`<I`)。同一鍵に複数町字がぶら下がる場合は `RecordTrie` が複数値を返すので、そのまま Jev の候補になる。

#### 同一鍵に複数の町字がぶら下がる割合

多値になるのは「入力の表記だけでは町字が決まらない」ときだけであるべきで、**データの持ち方の違いで多値になってはいけない**。同じ場所が 2 つの選択肢として Jev に出ると答えようがなく、確信度が割れて粒度が落ちる。

| | 町字 | 索引鍵 | 重複鍵 | `town.marisa` |
|---|---:|---:|---:|---:|
| 素朴に取り込む | 788,323 | 5,154,108 | 288,252 (5.59%) | 28.5 MB |
| Geolonia を畳む | 737,881 | 4,817,051 | 36,256 (0.75%) | 24.6 MB |
| **ABR 内も畳む** | **730,807** | **4,817,051** | **1,606 (0.033%)** | **24.3 MB** |

##### Geolonia の重複

突き合わせ鍵が大字・字の接頭辞を落としていなかった（ABR は `koaza='字新田'`、Geolonia は `koaza='新田'`）。段ごとに落としてから比べ、**一致したら行を足さず別名だけ既存の町字に向ける**。Geolonia 側の表記（`真狩村字光` に対し ABR は `光`）が別名として残るので、鍵はむしろ 74,202 本増える。

##### ABR 自身の重複 — 「字」は住所を変えない

ABR は同じ町字を「字青野」と「青野」の 2 レコードに分けて持つことがある（全国 3,816 組）。生データはこう:

```
mz=0369000 oaza_cho='字計根別北' efct_date=1947-04-17 status_flg=1 src_code=1
mz=0414000 oaza_cho='計根別北'   efct_date=1947-04-17 status_flg=1 src_code=1
```

`machiaza_id` 以外が同一。**`字` は「小字である」という構造の印であって名前の一部ではないので、これは同じ住所**。実データでも裏づけた:

- 鳥取県の 88 組すべてで片側の地番が **0 件**（幽霊エントリ）
- 栗原市の 3 組すべてで両側に地番があり、**空間的に隣接**して番号帯だけが割れている。`築館字青野` の実体（42-1〜101）は `築館青野`（1〜11）のすぐ隣
- `rsdt_addr_flg` / `src_code` / `machiaza_type` の**どれもペアを説明しない**（6 割は両側同じ値）

したがって 1 行にまとめる。ただし**地番が両方の `machiaza_id` に割れている**（栗原市築館新田は字あり側 324 筆、字なし側に別の 10 筆）ので、まとめた側の `machiaza_id` を `town.alt_machiaza` に残し、**層2 は全部引く**（`Geocoder._fetch_numbers`）。単なる重複削除ではなくデータ欠損の修正でもある。

効果（鳥取県 20,235 件、法人番号）:

| | 畳む前 | 畳んだ後 |
|---|---:|---:|
| 番号まで到達 | 95.74% | **95.76%** |
| 町字ファストパス | 19,700 | **20,111** |
| Jev 往復 | 424 | **322** (−24%) |
| 入力トークン | 1,108,729 | **917,485** (−17%) |
| 1,000 件あたり | $0.0023 | **$0.0019** |

`鳥取県八頭郡八頭町大字宮谷240番地15` は畳む前は幽霊側（地番 0 件）を選んで町字で止まっていたが、畳んだ後は地番まで到達する。

##### 残る 0.033%

1,606 鍵 / 344 組。内訳は (a) 大字と小字の**段の切り方**が違うもの 169 組（`霧多布東２条`+`２丁目` と `霧多布東２条２`）、(b) Geolonia の取りこぼし 87 組（`築館字外南沢` のように `字` が語中にあり接頭辞として落ちない）、(c) 段違いの同名 75 組、(d) 座標が離れた本当の別地 13 組。(d) 以外は追える余地があるが、実害が測れていないので追っていない。

#### 廃止住所の扱い

調査の結果、**`mt_town` には廃止住所がほぼ存在しない**。全 727,429 行のうち `ablt_date` が入っているのは **1 行**、`status_flg=3` が 24 行のみ。

したがって「廃止住所を索引に含める」という判断は実質的に無影響である。公式実装 (`digital-go-jp/abr-geocoder`) と揃えて **`status_flg ∈ {0,1,2}` を取り込み、`status_flg=3` の 24 行のみ除外**する。

**注意: 旧住所 → 現住所の自動変換は ABR 単体では実現できない。** `mt_town` に後継町字へのポインタが無いため。これが必要なら別データ源（自治体の町名変更告示等）が要る。本システムの範囲外とする。

#### 探索は 2 方向の完全一致だけ。曖昧一致はしない

marisa-trie は完全前方一致しかできない。そこで**両方向**に引く。

1. **索引鍵が入力の先頭** — ふつうの前方一致 (`prefixes`)。入力の 99.6% はここで決まる
2. **入力が市区町村・都道府県ちょうどで終わる** — 町字を探す余地が無い
3. **入力が索引鍵の先頭** (`keys`) — 入力が途中で終わっている場合。「鳥取県鳥取市面影」は ABR に行が無い（**丁目を持つ大字 22,797 件のうち、丁目なしの親エントリも在るのは 4,401 件＝19% だけ**）が、索引鍵の側がこの入力で始まっているので拾える。末尾の番地を削ってからもう一度試す
4. どれも当たらない誤字・異体字は、**町字を諦めて市区町村の粒度で返す**

**編集距離によるフォールバックは持たない。** 当初は入れていたが、実測で割に合わなかった。

| | 編集距離あり | 編集距離なし |
|---|---:|---:|
| 候補生成 | 433 µs/件 | **17 µs/件** |
| 7,191 件の処理時間 | 3.8 s | **1.06 s** |
| 町字への到達率 | 99.1% | 99.1%（変わらず） |

曖昧一致に落ちるのは全体の 0.3% で、そのうち正解を候補に含められたのは **44%**。実質 0.15% を拾うために全件のレイテンシが 25 倍になっていた。さらに編集距離は短いパターンほど距離が小さく出るため、「叶」「嶋」「新」のような 1 文字の町名が距離 1 で上位を占め、Jev に渡す選択肢を汚していた。

トライが候補集合の絞り込みを担い、精度判断は Jev に渡す、という原則1はそのまま。**絞り込みの手段を曖昧一致から完全一致 2 方向に置き換えただけ。**

### 3.2 層2: 番号ストア `abr.db`

対象は `mt_rsdtdsp_blk` / `mt_rsdtdsp_rsdt` / `mt_parcel` とその `_pos`。地番は全国で 1〜2 億件規模（佐々町 36,558 筆 / 32.2 km² からの外挿）。

アクセスパターンは**常に「ある町字の番号を全部」**であり、1件ずつ行で引くことはない。したがって行で持たず、**町字単位でパックした BLOB** として持つ。

**実測**（佐々町 `mt_parcel_city423912`、36,558 筆、25 町字、座標込み）:

| レイアウト | B/筆 | 全国1億筆 | 全国2億筆 |
|---|---:|---:|---:|
| 素の SQLite テーブル | 102.2 | 10.2 GB | 20.4 GB |
| `WITHOUT ROWID` | 60.8 | 6.1 GB | 12.2 GB |
| パック BLOB（無圧縮） | 10.5 | 1.1 GB | 2.1 GB |
| **パック BLOB + zlib** | **7.7** | **0.8 GB** | **1.5 GB** |
| パック BLOB + lzma | 7.1 | 0.7 GB | 1.4 GB |

**zlib を採る。** lzma との差は容量で 8% しかない一方、展開が 4 倍速く標準ライブラリで完結する。

削減が効いた順:

1. **1筆1行 → 1町字1 BLOB**（102 → 10.5 B、9.7倍）。行数が 1 億から 20 万に落ち、SQLite の行オーバーヘッドが消える。ここが支配的
2. **ID 列を捨てる** — `prc_id` / `blk_id` / `rsdt_id` は番号列のゼロ詰めであることを実測で確認済み（`blk_id←blk_num` 2,162 行、`rsdt_id←rsdt_num` 65,212 行、`prc_id←prc_num1/2/3` 36,558 行、いずれも不一致 0 件）。出力時に復元する
3. **番号を varint + 差分符号化** — 番号順にソートしてあるので第1番号の差分はほぼ 0 か 1
4. **座標を町字南西端からの差分の固定小数点**（1e-7 度 ≒ 1 cm）の varint
5. **町字 BLOB ごとに zlib 圧縮**

#### バイナリ仕様

SQLite テーブル `num_blob(lg_code INT, machiaza_id INT, kind INT, n INT, data BLOB, PRIMARY KEY(lg_code, machiaza_id, kind)) WITHOUT ROWID`。`kind` は 1=街区 / 2=住居番号 / 3=地番。

`data` の構造:

```
ヘッダ（非圧縮）
  u8      version
  i32     base_lat        町字内の最小緯度 x 1e7
  i32     base_lon        町字内の最小経度 x 1e7
  varint  n_entries
  varint  n_chunks
  チャンク目録  n_chunks x { varint first_num1, varint offset, varint length }

チャンク（各 256 エントリ、独立に zlib 圧縮）
  エントリごと:
    varint  d_num1        直前エントリからの差分
    varint  num2
    varint  num3          kind=3 (地番) のみ
    varint  d_lat         lat*1e7 - base_lat + 1   （0 は座標なしを表す）
    varint  d_lon         lon*1e7 - base_lon       （d_lat != 0 のときのみ）
```

**チャンク分割の理由。** 町字まるごとを展開すると実測で median 2.3 ms / max 9 ms（4,197 筆）かかる。256 エントリずつ独立に圧縮してチャンク目録を付けると、第1番号で二分探索して必要なチャンクだけ展開でき、**町字の大きさによらず 0.2 ms 程度**に収まる。

---

## 4. 正規化と建物名

入力側で行うのは **NFKC 正規化と空白（半角・全角）の除去のみ**。

**建物名・部屋番号は切り出さない。** 「〇〇マンション301」のような残余文字列は、パースせずそのまま Jev の `state` に渡す。建物名の切り出しは住所表記のロングテールそのもので、規則で書くと必ず破綻する。Jev は「301 は住居番号ではなく部屋番号だ」という判断を、実在する住居番号の一覧を見た上で下せる。

出力では残余文字列を未解決部分としてそのまま返す。

## 5. Jev の使い方

`POST https://api.typesafe.ai/v1/systemone` / Python SDK は `typesafe-sdk`。

### 5.1 2箇所で使う

**(a) 町字の確定** — 層1 の候補 N 件（**Choice の上限は 255 オプション**）から1つ選ばせる。

```
state:        { 入力: "<原文>", 正規化: "<NFKC後>" }
criteria:     { "c0": {住所: "鳥取県鳥取市面影一丁目"}, ..., "__none__": "候補のいずれでもない" }
instructions: "入力が指している住所はどれか"
```

**(b) 数値テールの解釈** — 「1-2-3」が *街区1・住居2 + 部屋3* なのか *地番1-2 の枝番3* なのかは、その町字が住居表示実施区域か (`rsdt_addr_flg`) と、実在する番号の並びを見ないと決まらない。層2 から取った実在レコードを Choice のオプションにして選ばせる。

**「候補のいずれでもない」は別の `Noul` ではなく Choice の選択肢として持たせる。** 当初は「候補に正解が含まれるか」を訊く `Noul` を並列で載せる設計だったが、予約オプション `__none__` を 1 つ足すほうが単純で、**該当なしの確率が選択肢と同じ分布の中に出る**ので解釈も一貫する。リクエストも 1 問で済む。

### 5.2 バッチ

入力 N 件を1リクエストに詰める。`state` に全入力を置き、質問を N 個並列に並べる（`instructions` から `state` のキーを参照する構造化指示）。公式クックブックで **12.2 倍安・10.0 倍速**の実績があるパターン。

段 (a) と段 (b) には依存関係があるため、**バッチ全体で合計 2 リクエスト**になる。

### 5.3 ファストパス

**層1 で厳密に最も長く一致した候補が 1 件だけなら Jev を呼ばない。** これは類似度の判断ではなく前方一致の定義そのものなので、トライが決めてよい。「大阪府高槻市奈佐原2丁目」と「大阪府高槻市大字奈佐原」が同時に当たったら前者。

同じ長さで複数並ぶ場合（京都市中京区に同名の「大文字町」が 4 つある等）と、曖昧一致に落ちた場合だけが Jev に回る。数値テールも層2 のレコードと一意に一致すれば同様に Jev を呼ばない。

**geolonia の難例 7,191 件での実測**:

| | 件数 | 割合 |
|---|---:|---:|
| ファストパス（Jev 不要） | 7,128 | **99.1%** |
| Jev: 同長の候補が競合 | 33 | 0.5% |
| Jev: 曖昧一致（異体字・ケ/ヶ の揺れ） | 29 | 0.4% |
| 候補なし | 1 | 0.0% |

最長一致のファストパスを入れる前は 12.2% が Jev 送りだった。**14 分の 1 に落ちている。** 残った 62 件は同名町・「箪笥町/簞笥町」・「緑が浜/緑ヶ浜」など、実際に判断が要るものばかり。

`--always-rerank` で無効化して、Jev 経路の精度を評価できるようにする。

### 5.4 confidence の使い方

confidence が閾値未満のとき、**結果を捨てずに粒度を1段上げて返す**。地番が決まらなければ町字の代表点を、町字が決まらなければ市区町村の代表点を返し、`level` フィールドでどこまで確かかを示す。TypeSafe の confidence-gated routing パターン。

**質問文と閾値は `config.py` 1ファイルに集約する。** TypeSafe のドキュメントが「人間がレビューすべきは質問と閾値だけ」と述べているとおり、これらが散らばるとレビュー不能になる。

## 6. API サーバを見据えた構造

- **コアは async ファースト。** `Geocoder` は不変の設定と接続ハンドルだけを持ち、グローバルな可変状態を持たない
- **CLI も将来の HTTP サーバも薄いアダプタ。** どちらも `Geocoder.geocode()` / `.geocode_many()` を呼ぶだけ
- **層1 は mmap、層2 は SQLite の読み取り専用接続。** どちらもプロセス間で安全に共有でき、ワーカーを増やしてもメモリが比例して増えない
- 最初に作るのは CLI のみ。HTTP サーバは同じコアの上に後から載せる

## 7. 構築コマンドの粒度

地番まで入れると構築に時間がかかるため、段階的に構築できるようにする。

```
build --level machiaza          # 層1のみ。全国 727k 件、数分、13 MB
build --level rsdt              # + 街区・住居番号
build --level parcel            # + 地番（フル）。1-2 GB
build --level parcel --pref 31  # 都道府県を絞る
```

## 8. 決定事項と根拠

| 決定 | 根拠 |
|---|---|
| トライは marisa-trie | 12.9 MB / mmap 0.2 ms / RSS 1 MB。dict トライは 1,322 MB で論外 |
| 町字まで全件常駐 | 12.9 MB で収まるため、遅延ロードも LRU も不要になり設計が1段単純になる |
| 番号層は町字単位パック BLOB | 102 → 7.7 B/筆。全国 1-2 億筆が 0.8-1.5 GB に収まる |
| 圧縮は zlib | lzma との容量差 8% に対し展開が 4 倍速く、標準ライブラリで完結 |
| BLOB を 256 件チャンク分割 | 町字の大きさによらず展開 0.2 ms（分割なしは max 9 ms） |
| ID 列を格納しない | 番号列のゼロ詰めであることを実測で確認（不一致 0 件） |
| 入力側の正規化は NFKC + 空白除去のみ | 手書き変換テーブルは永久メンテが必要で、漏れると黙って失敗する |
| 表記ゆれは索引側エイリアスで吸収 | ロジックではなくデータなので壊れない。1町字あたり平均 3.1 鍵 |
| 建物名は切り出さず Jev に渡す | 規則で書くと必ず破綻する。Jev は実在番号一覧を見た上で判断できる |
| 廃止住所も取り込む（実質無影響） | `ablt_date` は 727,429 行中 1 行のみ。公式実装と揃えて `status_flg=3` の 24 行だけ除外 |
| 地番の座標を持つ | 差分固定小数点 varint なので座標込みでも 7.7 B/筆 |

## 9. 未解決・将来

- **旧住所 → 現住所の変換**は ABR 単体では不可能（後継町字へのポインタが無い）。別データ源が要る
- **精度評価セット**が未整備。Jev 経路の効果を測るには、表記ゆれを含む入力と正解 ABR 識別子の対が要る
- **投機的ファンアウト**による Jev 往復の 2 回 → 1 回化。段 (a) の上位数件について段 (b) を先回りで問う。実装は後回し
- **差分更新**。ABR は定期更新されるため、DCAT フィードの更新日時を見て変更のあったファイルだけ再取り込みする
